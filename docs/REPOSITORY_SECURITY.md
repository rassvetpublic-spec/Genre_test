# Безопасность публичного репозитория

Этот файл задаёт минимальные правила защиты `Genre_test` от случайной публикации секретов и локальных учётных данных.

## Что нельзя коммитить

В Git не должны попадать:

- `.env` и локальные варианты `.env.*`;
- API-ключи, access tokens, пароли и Bearer-токены;
- приватные ключи и контейнеры сертификатов (`*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`);
- локальные credential-файлы (`credentials*.json`, `secrets*.json`, service-account JSON);
- пользовательские `.npmrc`, `.pypirc`, `.netrc` и другие файлы, способные содержать токены.

Шаблоны без реальных секретов допустимы только как явно обозначенные example/template-файлы.

## Автоматическая проверка

`.github/workflows/secret-scan.yml` запускает Gitleaks v8.30.1 для pull request, push в `main` и ручного запуска.

Проверка:

1. получает полную Git-историю;
2. подгружает все ветки и теги origin;
3. запускает Gitleaks по `--all --full-history`;
4. редактирует найденные значения в CI-логах (`--redact`);
5. завершает workflow ошибкой при обнаружении секрета.

CI дополняет, но не заменяет GitHub Secret Scanning и Push Protection на уровне настроек репозитория.

## Архивы и legacy-файлы

ZIP, архивные снимки и `legacy/` считаются таким же публичным содержимым, как обычный исходный код. Перед добавлением или заменой архива его содержимое должно отдельно проверяться на секреты и персональные данные.

## Если секрет уже попал в Git

Считать его скомпрометированным независимо от того, был ли файл позже удалён обычным коммитом.

Порядок действий:

1. revoke/отозвать секрет у провайдера;
2. выпустить новый credential;
3. убрать секрет из текущего дерева;
4. при необходимости переписать Git-историю отдельной контролируемой операцией;
5. повторить полный secret scan.

Удаление файла новым коммитом само по себе не делает опубликованный секрет безопасным.
