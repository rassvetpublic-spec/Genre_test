# Genre_test — русское описание проекта

> Локальная музыкальная лаборатория: анализ, поиск, сравнение, восстановление и подготовка музыки в одном понятном рабочем процессе.

## Что такое Genre_test

Genre_test начинался как локальный анализатор жанров, но постепенно развивается в полноценную систему для работы с музыкальной коллекцией и отдельными треками.

Главная идея простая: **загрузить аудиофайл и получить не набор непонятных цифр, а понятный музыкальный паспорт**, который можно использовать дальше — для поиска похожих треков, сортировки каталога, сравнения версий, восстановления проблемного аудио и подготовки финального результата.

Проект ориентирован прежде всего на локальную работу на Windows и современной NVIDIA-видеокарте. Основные функции должны оставаться доступными без обязательной отправки музыки в облако.

---

# 1. Что уже умеет проект

Текущая стабильная база умеет:

- анализировать один файл или целые каталоги;
- определять основной жанр и крупную жанровую семью;
- показывать вторичное жанровое влияние и близкие стили;
- определять BPM, тональность и лад;
- находить музыкальные признаки: настроение, инструменты, вокал и характер производства;
- анализировать технические свойства аудио;
- сохранять историю запусков;
- сравнивать результаты разных версий анализатора;
- отслеживать устойчивость результата при повторных анализах;
- работать в графическом интерфейсе;
- проверять состояние зависимостей и среды запуска;
- работать на CPU, а при наличии подходящей видеокарты использовать GPU;
- обрабатывать большие музыкальные коллекции пакетно;
- сохранять результаты в структурированном виде для последующей статистики и проверки.

Это фундамент, на котором строятся следующие этапы.

---

# 2. Главная цель

Genre_test должен превратиться в **единую локальную музыкальную рабочую станцию**, которая умеет пройти весь путь:

**аудиофайл → глубокий анализ → поиск и сравнение → исправление проблем → финальная обработка → проверка → метаданные → экспорт**

При этом пользователь должен иметь два уровня работы:

1. **Простой режим** — минимум настроек, понятные формулировки, автоматические решения.
2. **Экспертный режим** — подробные значения, промежуточные результаты, ручное управление и воспроизводимость.

---

# 3. Основные принципы проекта

## Локальная работа

Музыка должна анализироваться на компьютере пользователя. Облачные функции могут появляться как дополнительная возможность, но не как обязательное условие.

## Понятный результат

Вместо десятков разрозненных показателей система должна отвечать человеческим языком:

> Энергичный электронный трек с плотным низом, быстрым пульсом, яркой синтетической фактурой и напряжённым характером.

## Повторяемость

Если анализ повторить на той же версии системы и с теми же настройками, результат должен быть воспроизводим.

## Версионность

Каждый слой анализа должен иметь собственную версию. Это позволяет улучшать отдельные функции, не ломая всё приложение сразу.

## Честная уверенность

Система не должна изображать абсолютную уверенность. Если трек находится между двумя стилями или темп определяется неоднозначно, это должно быть видно пользователю.

## Безопасное развитие

Новые тяжёлые модели и экспериментальные функции не должны ломать стабильный базовый анализатор.

# 4. Roadmap

## v0.5 — Audio Intelligence

Цель версии: **научить Genre_test понимать трек глубже и сделать музыкальный поиск действительно полезным.**

### 4.1. Модульные результаты анализа

Вместо одного большого результата анализ будет разделён на независимые блоки:

- жанр;
- темп;
- тональность;
- настроение;
- энергия;
- характер;
- движение и грув;
- вокал;
- технический профиль;
- структура;
- сегменты;
- описание трека;
- поисковое представление трека.

Плюс такого подхода: любой блок можно обновить отдельно и всегда понятно, какой именно алгоритм дал конкретный результат.

### 4.2. Поиск похожей музыки

Пользователь выбирает один трек и получает список наиболее похожих по общему звучанию.

Поиск должен работать не только по жанру. Система должна учитывать общую музыкальную картину: тембр, ритм, плотность, настроение, динамику и другие признаки.

Пример:

> Выбрать трек → «Найти похожие» → получить 20 ближайших вариантов из локальной коллекции.

### 4.3. Поиск по текстовому описанию

Пользователь сможет написать обычную фразу:

> мрачная электронная музыка с женским вокалом и мощным припевом

или:

> спокойный ночной трек без вокала, медленный и атмосферный

Система должна найти подходящие композиции в локальной коллекции.

Русский язык должен быть полноценным рабочим сценарием, а не второстепенным дополнением.

### 4.4. Поиск по фрагменту

Можно будет искать музыку не только по целому треку, но и по конкретному участку.

Например:

- найти песни с похожим припевом;
- найти треки с похожим вступлением;
- найти похожий дроп;
- сравнить конкретные 30 секунд двух композиций.

### 4.5. Представительный фрагмент

Система автоматически выберет участок, который лучше всего представляет звучание композиции.

Это даст:

- более быстрый поиск;
- более удобное предварительное прослушивание;
- более честное сравнение длинных треков;
- возможность не анализировать одинаково подробно тишину, интро и основной музыкальный материал.

### 4.6. Карта структуры трека

Вместо одного результата на всю песню появится временная карта.

Пример:

- 00:00–00:24 — спокойное вступление;
- 00:24–01:02 — основной грув;
- 01:02–01:34 — более энергичная часть;
- 01:34–02:08 — припев;
- 02:08–02:32 — спад энергии.

В дальнейшем эта карта станет основой для восстановления, сравнения и обработки отдельных частей.

### 4.7. Core Sound — «ядро звучания»

Отдельный блок будет коротко отвечать на вопрос:

**«Как этот трек звучит в целом?»**

Он должен объединять:

- основной музыкальный характер;
- плотность;
- яркость или темноту;
- агрессивность или мягкость;
- электронность или акустичность;
- ритмическую направленность;
- общую атмосферу.

### 4.8. Энергия и эмоциональная динамика

Система должна оценивать не только настроение одним словом, а развитие эмоции по времени.

Планируются:

- общий уровень энергии;
- изменение энергии по треку;
- условная шкала «светлый ↔ мрачный»;
- условная шкала «спокойный ↔ возбуждённый»;
- резкие перепады;
- кульминации;
- эмоционально ровные участки.

### 4.9. Движение и грув

Отдельный анализ должен описывать, как музыка «движется»:

- ровно;
- качающе;
- пульсирующе;
- пружинисто;
- рублено;
- плавно;
- маршево;
- механически;
- быстро и бегуще;
- свободно, почти без ритмического пульса.

Это особенно полезно при поиске музыки с похожим ощущением движения.

### 4.10. Характер трека

Планируется набор понятных характеристик:

- мощный;
- тёплый;
- холодный;
- воздушный;
- эпичный;
- игривый;
- загадочный;
- роскошный;
- минималистичный;
- грубый;
- отполированный;
- ретро;
- современный;
- кинематографичный.

Характеристики должны быть контролируемыми и проверяемыми, а не случайным литературным описанием.

### 4.11. Улучшенный анализ темпа

BPM должен сопровождаться дополнительной информацией:

- уверенность в результате;
- возможный альтернативный темп;
- устойчивость оценки на разных участках;
- размер;
- предупреждение о типичных ошибках «в два раза быстрее» или «в два раза медленнее».

### 4.12. Улучшенный анализ вокала

Планируется определять:

- есть ли вокал вообще;
- насколько он доминирует;
- пение или рэп;
- одиночный вокал или группа;
- мужской, женский или смешанный вокальный профиль, когда это можно определить достаточно надёжно;
- плотность вокала по времени;
- участки без вокала;
- возможный голос за кадром или разговорную речь.

### 4.13. Технический паспорт трека

Genre_test должен выдавать отдельный блок измеряемых технических характеристик, например:

- длительность;
- частота дискретизации;
- число каналов;
- громкость;
- пики;
- динамический диапазон;
- спектральный баланс;
- яркость;
- низкочастотная энергия;
- стерео-параметры;
- переходные процессы;
- признаки перегруза или повреждённого файла.

Технические измерения должны быть отделены от музыкальных догадок.

### 4.14. Автоматическое описание

Из уже измеренных данных система сможет собрать короткое понятное описание без обязательного обращения к большой языковой модели.

Пример:

> Быстрый и энергичный электронный трек, основной стиль — Drum & Bass. Тёмный характер, выраженный синтетический низ, высокий уровень движения, вокал отсутствует. Темп около 174 BPM.

Главное требование: описание должно строиться из реальных результатов анализа, а не придумывать факты.

### 4.15. Фильтры каталога

Поиск можно будет ограничивать:

- жанром;
- крупной жанровой семьёй;
- BPM;
- тональностью;
- настроением;
- энергией;
- характером;
- наличием вокала;
- техническими параметрами;
- уровнем уверенности анализатора.

### 4.16. Монитор ресурсов

Отдельное окно должно показывать в реальном времени:

- загрузку процессора;
- использование оперативной памяти;
- память самого процесса Genre_test;
- загрузку видеокарты;
- занятую и свободную видеопамять;
- температуру GPU;
- энергопотребление, когда оно доступно;
- память, занятую моделями;
- текущий статус вычислений.

Функция не должна ломаться на компьютере без NVIDIA GPU.

### 4.17. Каталог и поиск в GUI

В графическом интерфейсе должны появиться отдельные рабочие зоны:

**Анализ | Каталог | Поиск | Сравнение | Проверка**

Пользователь не должен работать с базой данных вручную ради обычного поиска.

## v0.6 — Repair & Stem Lab

Цель версии: **не только находить проблемы, но и помогать исправлять их.**

### 4.18. Поиск дефектов

Система должна отмечать подозрительные участки:

- цифровой треск;
- щелчки;
- резкие выбросы;
- провалы;
- неестественные хвосты;
- металлические призвуки;
- плавающий фон;
- перегруз;
- слишком резкие высокие частоты;
- нестабильный низ;
- другие типичные дефекты генеративного или плохо обработанного аудио.

### 4.19. Восстановление проблемных участков

Планируется безопасный режим восстановления, где:

1. определяется проблемный участок;
2. создаётся копия;
3. применяется один или несколько вариантов исправления;
4. исходник остаётся нетронутым;
5. варианты можно сравнить.

Никакое автоматическое исправление не должно безвозвратно менять оригинал.

### 4.20. Ремонт вокала

Отдельная ветка должна работать с типичными проблемами вокала:

- резкие согласные;
- свистящие звуки;
- цифровая «стеклянность»;
- провалы;
- неестественные переходы;
- слишком шумные вдохи;
- отдельные артефакты;
- нестабильная громкость;
- странные окончания фраз.

### 4.21. Работа со стемами

Планируется режим разделения трека на основные части и последующей работы с ними.

Базовые группы:

- вокал;
- ударные;
- бас;
- остальная музыка.

В дальнейшем количество групп может расширяться.

### 4.22. Ремонт после разделения

Разделение само по себе может создавать артефакты. Поэтому система должна уметь:

- оценивать качество полученных дорожек;
- находить «протечки» соседних инструментов;
- сглаживать проблемные места;
- сравнивать восстановленный микс с оригиналом;
- контролировать, чтобы исправление не стало хуже исходника.

## v0.7 — Studio Finish

Цель версии: **доводить трек до законченного состояния и объективно сравнивать варианты.**

### 4.23. Оркестратор финальной обработки

Появится единый сценарий, который сможет:

- проанализировать материал;
- выбрать безопасный план обработки;
- создать несколько кандидатов;
- отрендерить их;
- измерить результат;
- сравнить версии;
- предложить лучший вариант;
- сохранить все шаги обработки.

Автоматика должна оставлять возможность ручного вмешательства.

### 4.24. Синхронное A/B/X-сравнение

Пользователь сможет сравнивать версии одного трека без разницы в позиции воспроизведения.

Функции:

- мгновенное переключение между версиями;
- одинаковая точка времени;
- выравнивание воспринимаемой громкости;
- слепое сравнение;
- заметки;
- фиксация победителя;
- сравнение отдельных фрагментов.

### 4.25. Набор кандидатов

Вместо одного «магического» результата система сможет создавать несколько осторожно различающихся вариантов:

- мягче;
- плотнее;
- ярче;
- темнее;
- шире;
- более ударно;
- более динамично.

Затем варианты сравниваются по измерениям и прослушиванию.

### 4.26. Контроль ухудшений

После любой обработки система должна проверять:

- не появилась ли перегрузка;
- не разрушилась ли стерео-картина;
- не потерялись ли ударные;
- не стал ли вокал хуже;
- не исчезла ли динамика;
- не появились ли новые артефакты;
- не изменилась ли громкость так сильно, что сравнение стало нечестным.

## v0.8 — Metadata, Catalog & Delivery

Цель версии: **привести в порядок коллекцию и подготовить результат к хранению и публикации.**

### 4.27. Аудитор метаданных

Система должна находить:

- пустые теги;
- противоречивые жанры;
- неверные номера треков;
- мусорные поля;
- странные названия;
- проблемы с кодировкой;
- несовпадения между именем файла и тегами.

### 4.28. Пакетное исправление

Перед изменением сотен файлов программа показывает план:

- что будет изменено;
- какие файлы затронуты;
- старое значение;
- новое значение;
- возможность отмены.

### 4.29. Умная организация каталога

Планируются инструменты для:

- группировки похожих треков;
- поиска музыкальных кластеров;
- обнаружения выбросов;
- поиска почти одинаковых версий;
- поиска дублей;
- сортировки больших папок;
- формирования подборок по музыкальным признакам.

### 4.30. Локальное хранилище материалов

Каждый важный файл сможет иметь историю:

- исходник;
- производные версии;
- результаты анализа;
- промежуточные рендеры;
- финалы;
- метаданные;
- контрольные суммы;
- описание выполненных операций.

Главная задача — всегда понимать, **откуда взялся конкретный файл и что с ним происходило**.

### 4.31. Профили экспорта

Пользователь сможет выбрать понятную цель:

- архив;
- стриминг;
- видео;
- рабочая копия;
- отправка заказчику;
- дальнейшая обработка.

Система проверит, соответствует ли итоговый файл выбранному профилю.

## v0.9 — Visual Workflow & Runtime

Цель версии: **сделать сложные цепочки обработки визуальными и научить систему разумно управлять тяжёлыми моделями.**

### 4.32. Визуальный конструктор

Пользователь сможет собирать процесс из блоков:

**Загрузить → Проанализировать → Найти дефекты → Разделить → Исправить → Сравнить → Экспортировать**

Это позволит создавать собственные сценарии без написания Python-кода.

### 4.33. Менеджер моделей и видеопамяти

На видеокарте нельзя держать все тяжёлые модели одновременно. Поэтому система должна:

- знать, какие модели сейчас загружены;
- оценивать свободную VRAM;
- выгружать ненужную модель;
- загружать следующую;
- не запускать несовместимые задачи одновременно;
- уметь работать очередью;
- восстанавливаться после неудачного задания;
- показывать пользователю, почему задача ждёт.

### 4.34. Очередь задач

Планируются:

- очередь анализов;
- приоритеты;
- пауза;
- продолжение;
- отмена;
- повтор только неудачных задач;
